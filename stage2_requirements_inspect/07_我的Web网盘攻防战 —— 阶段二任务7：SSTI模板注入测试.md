# 我的Web网盘攻防战 —— 阶段二任务7：SSTI模板注入测试

## 写在前面：模板引擎是帮你生成页面的，不是执行用户输入的

很多Web框架会使用模板引擎生成页面。例如 Flask 常用 Jinja2，Java Web 可能使用 Thymeleaf、Freemarker、Velocity 等。模板引擎本来是为了把变量安全地填进HTML，但如果开发者把用户输入当作模板内容再次渲染，就可能出现 SSTI（Server-Side Template Injection，服务端模板注入）。简单说：用户输入不应该变成模板语法被服务器执行。

> **边界提醒**：本任务只允许在自己小组的网盘靶场、课程指定互测靶场、虚拟机或本机 `localhost` 中完成。不要扫描、爆破、上传、探测任何未授权网站、校园系统、云服务或他人真实业务系统。所有攻击动作都必须可回滚、可截图、可复现，不以破坏数据为目标。

## 第1步：判断你的系统是否使用模板引擎

Flask 的 `render_template("index.html", name=name)` 使用 Jinja2；Spring Boot 的 `templates/*.html` 常用 Thymeleaf；Java还可能使用 Freemarker、Velocity、JSP表达式；纯静态HTML + 后端拼字符串不一定是模板引擎，但也可能有XSS。你要记录使用的框架、页面如何生成、有没有把用户输入拼进模板字符串再渲染。

---

## 第2步：找到可能触发SSTI的输入点

SSTI通常出现在错误页面把用户输入拼成模板、管理员公告支持“模板变量”、用户自定义欢迎语、搜索结果页面动态生成模板字符串、为了图省事使用 `render_template_string` 等位置。

Flask危险写法示例：

```python
from flask import request, render_template_string

@app.route('/hello')
def hello():
    name = request.args.get('name', '')
    template = '<h1>Hello ' + name + '</h1>'
    return render_template_string(template)
```

这里的危险点是：`name` 被拼进了模板内容，再由模板引擎解析。更安全的写法是使用固定模板文件：

```python
@app.route('/hello')
def hello():
    name = request.args.get('name', '')
    return render_template('hello.html', name=name)
```

模板中写：

```html
<h1>Hello {{ name }}</h1>
```

这时 `name` 是变量值，不是模板语法。

## 第3步：使用无害数学表达式探测

课程中只使用无害数学表达式：

```text
{{7*7}}
```

测试时把它输入到昵称、搜索框、欢迎语、错误参数等位置，观察页面显示：如果显示原样 `{{7*7}}`，通常不说明SSTI；如果显示 `49`，说明服务端模板引擎可能执行了用户输入；如果页面报模板语法错误，也要记录，可能说明输入进入了模板解析流程。

测试示例：

```text
http://127.0.0.1:5000/hello?name={{7*7}}
```

期望安全结果是 `Hello {{7*7}}`，危险结果是 `Hello 49`。本课程不要求用SSTI读取服务器文件、执行系统命令、访问环境变量或扩展到远程控制。发现 `{{7*7}}` 被执行，就足够证明漏洞存在。

## 第4步：区分SSTI和XSS

| 对比 | XSS | SSTI |
| --- | --- | --- |
| 执行位置 | 浏览器 | 服务器模板引擎 |
| 典型标记 | `<script>alert(1)</script>` | `{{7*7}}` |
| 直接影响 | 访问页面的用户 | 服务器端渲染流程 |
| 根因 | 输出到HTML前未编码 | 用户输入被当模板解析 |

如果 `<script>` 执行，是XSS；如果 `{{7*7}}` 变成 `49`，是SSTI迹象。两者可能同时存在，但不要混为一谈。

---

## 第5步：修复SSTI

不要渲染用户提供的模板字符串，避免 `render_template_string(user_input)` 或等价写法。用户输入只能作为变量值传入模板，不能作为模板本身。错误页面不要把错误参数拼进模板字符串，显示固定提示即可。如果业务确实需要“自定义模板”，需要严格沙箱、白名单变量、权限隔离和审计，大一课程项目不建议实现这种功能。

### 漏洞报告至少写清楚

- 漏洞类型：例如 SQL注入 / XSS / CSRF / 越权下载。
- 漏洞位置：完整 URL、接口路径、请求方法、关键参数。
- 测试环境：本机、虚拟机或课程互测靶场；测试时间；测试账号。
- 复现步骤：从登录、构造请求到观察结果，每一步都要截图或保存请求包。
- 影响说明：能造成什么后果，不能夸大；例如“可绕过登录进入文件列表”，不要写成“可控制服务器”。
- 修复建议：说明根因、给出修复方式，并附修复后同样步骤无法成功的证明。

### 修复时的共同原则

1. 不要只在前端过滤。浏览器里的限制都可以被 F12、代理工具或脚本绕过，后端必须做真正校验。
2. 不要只黑名单过滤某几个字符。优先采用白名单、参数化查询、框架内置安全机制、权限统一拦截。
3. 不要修一个接口漏一个接口。文件展示、下载、删除、重命名、分享等同类接口都要统一检查。
4. 修复后一定要用“原来的攻击参数”再测一遍，证明漏洞确实失效。

## 最后的提醒

模板引擎很强大，所以更不能把用户输入交给它当模板执行。请记住：模板是开发者写的，变量才是用户输入。
