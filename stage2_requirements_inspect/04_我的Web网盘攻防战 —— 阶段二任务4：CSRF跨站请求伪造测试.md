# 我的Web网盘攻防战 —— 阶段二任务4：CSRF跨站请求伪造测试

## 写在前面：已登录，不代表这次操作真是本人发起的

假设你已经登录了网盘。此时浏览器会自动带上你的 Cookie。攻击者如果诱导你打开一个页面，这个页面偷偷向你的网盘发送“删除文件”请求，浏览器也可能自动带上登录 Cookie。服务器看到 Cookie，以为是你本人操作，于是文件被删除。这就是 CSRF。本任务要学习的是：对会改变状态的操作，不能只靠Cookie判断身份，还要确认请求确实来自当前页面和当前用户意图。

> **边界提醒**：本任务只允许在自己小组的网盘靶场、课程指定互测靶场、虚拟机或本机 `localhost` 中完成。不要扫描、爆破、上传、探测任何未授权网站、校园系统、云服务或他人真实业务系统。所有攻击动作都必须可回滚、可截图、可复现，不以破坏数据为目标。

## 第1步：找到会改变状态的接口

只要请求会让服务器数据发生变化，就是改变状态。例如删除文件 `/delete?filename=a.txt`、修改昵称 `/profile/update`、修改密码 `/password/change`、创建分享链接 `/share/create`、取消分享 `/share/delete`。文件下载通常是读取操作，CSRF影响相对小；删除、修改、创建这类接口更重要。

如果你的删除接口是 `GET /delete?filename=test.txt`，就非常适合本任务。GET请求很容易被图片、链接、脚本触发，不应该用于删除这类危险操作。

---

## 第2步：判断接口是否只靠Cookie

测试方法：登录用户A；在文件列表中正常删除一个测试文件，抓取或记录请求；再上传一个新测试文件；直接在地址栏、Postman或浏览器控制台重放删除请求；观察是否不需要额外确认就删除成功。

你要观察请求中是否有随机Token，Token是否每个表单不同或每个会话不同，后端是否校验Token，请求方法是否为POST，Cookie是否设置了SameSite属性。如果只要浏览器带着Cookie，请求就能成功，说明具备CSRF风险条件。

## 第3步：构造本地CSRF演示页

在你自己的电脑上创建一个本地HTML文件，用它模拟“第三方页面”。不要上传到公网，不要发给无关同学。

如果目标接口是GET删除：

```html
<!DOCTYPE html>
<html>
<body>
  <h3>这是课程CSRF演示页</h3>
  <img src="http://127.0.0.1:5000/delete?filename=csrf_test.txt" style="display:none">
  <p>如果你已登录靶场，并且文件被删除，说明接口存在CSRF风险。</p>
</body>
</html>
```

测试步骤：登录网盘，上传 `csrf_test.txt`，在同一浏览器打开本地HTML文件，回到文件列表刷新，观察文件是否被删除。

如果目标接口是POST，可以构造一个自动提交表单：

```html
<!DOCTYPE html>
<html>
<body onload="document.forms[0].submit()">
  <form action="http://127.0.0.1:5000/delete" method="POST">
    <input type="hidden" name="filename" value="csrf_test.txt">
  </form>
</body>
</html>
```

这只是课程演示。不要把CSRF页面用于真实网站，不要诱导别人点击。

## 第4步：分析漏洞原因

CSRF成立通常需要同时满足：用户已经登录目标系统；浏览器自动带上认证Cookie；目标接口会改变状态；服务器没有校验CSRF Token或同源约束；操作参数可以被攻击者猜到或构造。你要在报告中逐条说明自己的系统满足了哪些条件。

---

## 第5步：修复CSRF

删除、修改、创建操作不要使用GET，至少改成POST表单。但只改POST还不够，CSRF仍可通过自动提交表单触发。更完整的修复是增加CSRF Token：服务器生成随机Token，放入用户Session和表单中；提交时，后端比较两者是否一致。

```text
打开页面时：
  token = random()
  session.csrf_token = token
  表单隐藏字段 csrf_token = token

提交删除时：
  if request.csrf_token != session.csrf_token:
      reject("CSRF校验失败")
  else:
      执行删除
```

同时可以设置 Cookie `SameSite=Lax` 或 `SameSite=Strict`。删除文件时仍然要检查用户是否登录、文件是否属于当前用户、CSRF Token是否正确。CSRF防御不能替代越权检查。

### 漏洞报告至少写清楚

- 漏洞类型：例如 SQL注入 / XSS / CSRF / 越权下载。
- 漏洞位置：完整 URL、接口路径、请求方法、关键参数。
- 测试环境：本机、虚拟机或课程互测靶场；测试时间；测试账号。
- 复现步骤：从登录、构造请求到观察结果，每一步都要截图或保存请求包。
- 影响说明：能造成什么后果，不能夸大；例如“可绕过登录进入文件列表”，不要写成“可控制服务器”。
- 修复建议：说明根因、给出修复方式，并附修复后同样步骤无法成功的证明。

### 修复时的共同原则

1. 不要只在前端过滤。浏览器里的限制都可以被 F12、代理工具或脚本绕过，后端必须做真正校验。
2. 不要只黑名单过滤某几个字符。优先采用白名单、参数化查询、框架内置安全机制、权限统一拦截。
3. 不要修一个接口漏一个接口。文件展示、下载、删除、重命名、分享等同类接口都要统一检查。
4. 修复后一定要用“原来的攻击参数”再测一遍，证明漏洞确实失效。

## 最后的提醒

CSRF最容易被忽略，因为攻击请求看起来“确实来自用户浏览器”。但安全系统不能只问“你是谁”，还要问“这个操作真的是你主动发起的吗”。
