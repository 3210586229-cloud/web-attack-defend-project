# 我的Web网盘攻防战 —— 阶段二任务1：弱口令与密码爆破测试

## 写在前面：登录页面是网盘的大门

你们已经做出了登录功能。现在换一个角度想：如果一个用户把密码设置成 `123456`，或者系统没有限制连续登录失败次数，那么攻击者是不是可以不断尝试密码，直到猜中为止？这次任务要学习的是认证安全测试，重点包括弱口令、低速可控的密码爆破实验、登录失败限速、账号锁定、统一错误提示和日志记录。

> **边界提醒**：本任务只允许在自己小组的网盘靶场、课程指定互测靶场、虚拟机或本机 `localhost` 中完成。不要扫描、爆破、上传、探测任何未授权网站、校园系统、云服务或他人真实业务系统。所有攻击动作都必须可回滚、可截图、可复现，不以破坏数据为目标。

## 第2步：手工验证弱口令

打开登录页面，手工尝试几个弱密码组合，观察能否成功登录。例如：

```text
用户名：admin
密码：admin
```

```text
用户名：user1
密码：123456
```

如果登录成功，说明系统至少存在弱口令风险。这里的漏洞不一定来自代码 bug，而可能来自业务策略缺失：系统允许用户设置过于简单的密码。记录登录页面 URL、测试账号、是否能成功登录、登录成功后的页面截图、系统有没有提示“密码太简单”。

不要把弱口令和SQL注入混在一起。弱口令是密码真的猜对了；SQL注入是通过特殊输入改变SQL语义。两者都可能绕过登录，但原理完全不同。

### ✅ 第2步完成标志

- 至少验证一个弱口令账号；
- 能说明弱口令风险的根因是“密码策略不足”；
- 截图中能看到登录前后变化。

## 第3步：低速、可控地测试登录失败限制

在课程靶场中，连续尝试多个错误密码，观察系统是否有以下保护：连续失败 5 次后是否临时锁定；是否要求等待一段时间；是否出现验证码；是否记录失败日志；是否对同一 IP、同一账号分别计数。

你可以手工测试，也可以写一个低速脚本，每隔 1-2 秒尝试一次课程小字典中的密码。脚本只允许用于本机或课程授权靶场。

```python
import time
import requests

url = "http://127.0.0.1:5000/login"
username = "user1"
passwords = ["111111", "abc123", "password", "123456"]

for pwd in passwords:
    r = requests.post(url, data={"username": username, "password": pwd}, timeout=5)
    print(pwd, r.status_code, r.text[:80])
    time.sleep(2)  # 低速测试，不要高频请求
```

### 可选工具：Hydra 登录测试工具

除了手工测试和 Python 小脚本，本任务允许使用 **Hydra** 作为推荐工具之一。Hydra 是常见的认证接口安全测试工具，支持对多种登录协议或登录表单进行口令尝试。在本课程中，Hydra 只用于帮助你理解“登录接口如果没有限速，就会被重复尝试”这一安全问题，不用于追求速度，也不用于真实网站。

> **工具使用边界**：只允许对 `127.0.0.1`、本机虚拟机、自己小组网盘靶场或教师明确授权的互测靶场使用；只允许使用 5-10 行课程小字典；只允许单线程或极低并发测试；不要导入泄露密码库、真实社工字典或大规模字典；不要对校园统一认证、邮箱、云服务器、Git平台、真实网盘或任何未授权系统使用。

#### 1. 先确认登录表单的三个关键信息

使用 Hydra 之前，不要直接复制命令。你需要先打开浏览器开发者工具，观察登录请求，确认下面三件事：

```text
登录接口路径：例如 /login
请求方法：例如 POST
参数名称：例如 username=xxx&password=yyy
失败特征：例如页面返回“用户名或密码错误”
成功特征：例如跳转到 /index 或页面出现“我的文件”
```

Hydra 不是“自动理解网页”的工具。它需要你告诉它用户名参数叫什么、密码参数叫什么，以及什么响应代表失败或成功。如果参数名写错，Hydra 的结果就没有意义。

#### 2. 准备课程专用字典文件

在本机新建一个 `passwords.txt` 文件，只写课程测试密码，例如：

```text
111111
abc123
password
123456
A_test_password_2026!
```

如果需要测试多个用户名，也可以准备 `users.txt`：

```text
user1
user2
admin
```

注意：这里的字典必须小。课程目标是验证登录接口是否有限速、锁定和日志，而不是进行真实爆破。

#### 3. 基本命令结构

假设你的网盘运行在 `http://127.0.0.1:5000`，登录接口是 `/login`，登录参数是 `username` 和 `password`，登录失败时页面中会出现“用户名或密码错误”，可以使用下面的课程示例：

```bash
hydra -l user1 -P passwords.txt -s 5000 -V -f -t 1 127.0.0.1 http-post-form "/login:username=^USER^&password=^PASS^:F=用户名或密码错误"
```

参数含义如下：

```text
-l user1        指定一个测试用户名
-P passwords.txt 从文件中读取测试密码
-s 5000         指定目标端口，这里对应本机 5000 端口
-V              显示每一次尝试过程，便于截图和分析
-f              找到一个可用口令后停止，不继续尝试
-t 1            使用单线程，避免高并发请求
127.0.0.1       目标主机，只允许写本机或授权靶场地址
http-post-form  说明测试的是 HTTP POST 登录表单
^USER^          Hydra 自动替换为当前用户名
^PASS^          Hydra 自动替换为当前密码
F=用户名或密码错误  失败判断条件：响应中包含该内容时视为登录失败
```

如果你要从 `users.txt` 中读取多个课程测试用户名，可以改为：

```bash
hydra -L users.txt -P passwords.txt -s 5000 -V -f -t 1 127.0.0.1 http-post-form "/login:username=^USER^&password=^PASS^:F=用户名或密码错误"
```

其中 `-L users.txt` 表示从文件读取多个用户名。课程中不建议使用大量用户名，只需要 2-3 个课程账号即可。

#### 4. 如何判断 Hydra 输出是否可信

Hydra 输出“找到密码”不等于一定真的成功。你必须人工复核：

```text
第一，看它使用的是不是课程账号；
第二，看它命中的密码是否确实能手工登录；
第三，看登录后是否进入了正确的用户空间；
第四，看服务器日志中是否记录了失败尝试和成功登录；
第五，看多次失败后系统是否触发锁定、等待或验证码。
```

如果 Hydra 一下子报出很多“成功”，通常不是系统真的有这么多密码，而是失败条件写错了。例如你的页面失败提示是“账号或密码错误”，但命令里写成“用户名或密码错误”，Hydra 可能就无法正确识别失败响应。

#### 5. 常见问题排查

如果 Hydra 没有得到预期结果，优先检查以下内容：

```text
表单参数名是否正确：username/password 还是 user/pass？
登录接口路径是否正确：/login 还是 /user/login？
端口是否正确：5000、8080、80 是否写对？
失败提示是否完全匹配：中文、空格、标点是否一致？
系统是否使用 JSON 登录：如果是 JSON，需要改用更合适的脚本方式测试。
系统是否启用了 CSRF Token：如果每次请求 token 都变化，Hydra 可能无法直接完成测试。
系统是否已经加了锁定策略：这时 Hydra 应该无法继续有效尝试，这说明防护生效。
```

#### 6. 本任务中 Hydra 的正确学习目标

你使用 Hydra 后，报告中不要只写“我用 Hydra 爆破出了密码”。更好的写法是：

```text
我使用 Hydra 对课程靶场登录接口进行了 5 次低速口令尝试。测试发现，在连续失败后，系统仍未触发账号锁定、等待时间或验证码；服务器日志只记录了成功登录，没有记录失败登录。因此，该登录接口存在密码爆破防护不足问题。修复后，同样命令在第 5 次失败后被服务端拦截，正确密码也需要等待锁定时间结束后才能登录。
```

这样写才能体现你真正理解了认证安全测试：工具只是手段，漏洞判断依靠的是系统行为、日志证据和修复前后对比。

观察点包括：错误密码尝试很多次后系统仍然正常返回“密码错误”，说明可能没有限速；登录失败提示写成“用户名不存在”或“密码错误”，说明可能存在账号枚举风险；正确密码在多次失败后仍可立即登录，说明没有临时锁定；服务器日志没有任何失败记录，说明后续很难追踪攻击行为。

## 第4步：分析漏洞原因

弱口令和爆破风险通常来自下面几个原因：注册时没有密码强度要求；登录失败没有计数；失败后不等待，接口可以被反复调用；提示过于精确，帮助攻击者确认账号是否存在；没有日志，无法发现异常登录行为。你需要把自己系统的问题对应到上面几点中，不要只写“有漏洞”。

---

## 第5步：完成安全加固

注册接口应检查密码长度和复杂度。课程阶段可以采用简单规则：长度至少 8 位；不允许与用户名相同；不允许出现在弱口令列表中；至少包含字母和数字。

```text
if len(password) < 8:
    reject("密码长度至少8位")
if password == username:
    reject("密码不能与用户名相同")
if password in weak_password_list:
    reject("密码过于常见")
```

登录失败限制可以先做简单版本：同一账号连续失败 5 次，锁定 5 分钟；锁定信息放在服务端，不要只放前端；登录成功后清空失败计数；返回统一提示“用户名或密码错误”。日志至少记录登录成功/失败、用户名、时间、IP地址、失败原因大类。注意：日志里不要明文记录密码。

### 漏洞报告至少写清楚

- 漏洞类型：例如 SQL注入 / XSS / CSRF / 越权下载。
- 漏洞位置：完整 URL、接口路径、请求方法、关键参数。
- 测试环境：本机、虚拟机或课程互测靶场；测试时间；测试账号。
- 复现步骤：从登录、构造请求到观察结果，每一步都要截图或保存请求包。
- 影响说明：能造成什么后果，不能夸大；例如“可绕过登录进入文件列表”，不要写成“可控制服务器”。
- 修复建议：说明根因、给出修复方式，并附修复后同样步骤无法成功的证明。

## 最后的提醒

登录接口是系统的第一道门。门本身写得再漂亮，如果钥匙是 `123456`，或者门锁允许别人试一万次，那也不安全。本任务学会的不是“猜密码”，而是理解认证系统必须让攻击者付出成本。
