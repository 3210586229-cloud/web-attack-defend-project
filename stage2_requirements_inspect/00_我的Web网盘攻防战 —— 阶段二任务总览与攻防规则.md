# 我的Web网盘攻防战 —— 阶段二任务总览与攻防规则

## 写在前面：靶子已经准备好了，现在开始真正的攻防

嘿，同学！恭喜你们已经完成了网盘的基本功能：注册、登录、文件上传、文件列表、文件下载。到这里，你们手上已经有了一个可以运行的“靶子”。接下来要做的事情不是继续堆功能，而是像安全测试人员一样看自己的系统：登录接口能不能被绕过？下载接口会不会把别人的文件也给我？上传功能会不会让别人把危险文件放进服务器？删除、修改、分享这些操作有没有确认“这个用户有没有权限做”？

本阶段的目标不是“黑掉别人”，而是通过可控实验理解漏洞如何产生、如何发现、如何复现、如何修复。你们会轮流扮演两个角色：白帽子负责授权测试和漏洞报告，开发者/防守方负责复现、定位根因、完成加固并写安全加固报告。

> **边界提醒**：本任务只允许在自己小组的网盘靶场、课程指定互测靶场、虚拟机或本机 `localhost` 中完成。不要扫描、爆破、上传、探测任何未授权网站、校园系统、云服务或他人真实业务系统。所有攻击动作都必须可回滚、可截图、可复现，不以破坏数据为目标。

## 推荐攻防流程：不要一上来就乱点

### 第一步：确认授权范围

每个小组只能测试课程指定目标，例如“本组自测”或“按分组攻击下一组”。如果对方没有把某个地址、接口或账号提供给你，就不要测试。尤其不要对公网 IP 做大范围扫描，不要扫学校资产，不要扫云服务器的其他端口。

### 第二步：准备测试账号和快照

每个小组至少准备两个普通用户账号，例如 `user1 / 123456` 和 `user2 / 123456`；准备两个测试文件，例如 `user1_secret.txt`、`user2_secret.txt`；准备虚拟机或云服务器快照，修坏了能恢复。测试越权、文件读取、CSRF时，至少需要两个用户。只用一个账号，很多漏洞是测不出来的。

### 第三步：先正常使用，再异常测试

每个漏洞都按这个思路来：先用正常功能走一遍，记录正常请求长什么样；再只改一个参数，例如文件名、用户ID、文件ID、密码字段；观察响应变化，包括状态码、页面内容、跳转位置、文件是否下载成功、数据库是否变化；最后形成结论：是漏洞、不是漏洞、还是需要更多证据。

### 第四步：漏洞报告与修复报告配对提交

攻击方写漏洞报告，防守方写安全加固报告。两份报告要能对应起来：攻击方的复现参数，防守方必须拿来再测一次。

### 漏洞报告至少写清楚

- 漏洞类型：例如 SQL注入 / XSS / CSRF / 越权下载。
- 漏洞位置：完整 URL、接口路径、请求方法、关键参数。
- 测试环境：本机、虚拟机或课程互测靶场；测试时间；测试账号。
- 复现步骤：从登录、构造请求到观察结果，每一步都要截图或保存请求包。
- 影响说明：能造成什么后果，不能夸大；例如“可绕过登录进入文件列表”，不要写成“可控制服务器”。
- 修复建议：说明根因、给出修复方式，并附修复后同样步骤无法成功的证明。

### 修复时的共同原则

1. 不要只在前端过滤。浏览器里的限制都可以被 F12、代理工具或脚本绕过，后端必须做真正校验。
2. 不要只黑名单过滤某几个字符。优先采用白名单、参数化查询、框架内置安全机制、权限统一拦截。
3. 不要修一个接口漏一个接口。文件展示、下载、删除、重命名、分享等同类接口都要统一检查。
4. 修复后一定要用“原来的攻击参数”再测一遍，证明漏洞确实失效。

## 本阶段统一提交材料

每个小组在阶段二结束时至少提交漏洞报告包、安全加固报告包、关键截图或录屏、源码压缩包或仓库链接、答辩准备清单。报告中要标明修复前版本和修复后版本，建议使用 Git tag，例如 `vuln-sql`、`fixed-sql`。

## AI使用建议

你可以把 AI 当作“安全学习助教”，但不要让它替你直接糊弄报告。推荐这样问：“我正在课程靶场测试自己写的网盘系统。请解释 SQL 注入为什么能绕过登录，并用伪代码说明根因。”不推荐这样问：“帮我攻击某某真实网站”“给我写免杀木马”“帮我绕过别人的安全设备”。这些都不属于本课程任务。

## 最后的提醒

这一阶段真正重要的不是“payload背下来”，而是形成一套思维：输入从哪里来、后端信任了什么、权限在哪里检查、输出有没有编码、危险操作有没有确认。当你能用这套思维审视自己的代码时，你就已经从“会写功能”走向“会写安全的功能”了。
