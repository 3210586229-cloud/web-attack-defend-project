# 我的Web网盘攻防战 —— 阶段二任务6：文件上传漏洞、WebShell与木马文件识别测试

## 写在前面：网盘最核心的功能，也可能是最危险的入口

网盘允许用户上传文件，这是功能需求；但如果上传功能没有限制，用户就可能上传脚本文件、伪装文件、超大文件、危险压缩包，甚至让服务器把上传的文件当代码执行。本任务会学习文件上传漏洞、WebShell风险、木马文件识别，以及常见 WebShell 管理工具的安全认知。

这里的“木马”和“WebShell”只做安全认知、风险验证、日志分析和防护加固，不编写免杀、隐藏、持久化、远控、反连、提权、横向移动类程序。本课程所有演示文件都必须是无害样本，只用于证明上传校验缺失或上传目录执行权限配置不当。

> **边界提醒**：本任务只允许在自己小组的网盘靶场、课程指定互测靶场、虚拟机或本机 `localhost` 中完成。不要扫描、爆破、上传、连接、探测任何未授权网站、校园系统、云服务或他人真实业务系统。所有攻击动作都必须可回滚、可截图、可复现，不以破坏数据为目标。

## 第1步：梳理上传接口

先把上传流程画出来：

```text
浏览器选择文件
    ↓
POST /upload
    ↓
后端解析文件
    ↓
保存到 upload/用户名/
    ↓
文件列表展示
    ↓
/download 下载
```

记录上传接口URL和请求方法、表单字段名、文件保存路径、上传后能否通过URL直接访问、文件名是否保留原名、是否限制大小、类型、数量。

### ✅ 第1步完成标志

- 写清楚上传接口路径，例如 `/upload`；
- 写清楚上传字段名，例如 `file`、`uploadFile`；
- 写清楚文件保存目录；
- 写清楚上传后是“直接URL访问”还是“后端下载接口读取”。

------

## 第2步：测试扩展名限制

观察系统是否允许上传明显不应该作为网盘普通文件执行的脚本类型。课程测试文件建议使用无害内容：

```text
文件名：test.jsp
内容：COURSE_UPLOAD_TEST_ONLY
```

或者：

```text
文件名：test.php
内容：COURSE_UPLOAD_TEST_ONLY
```

你只需要测试系统是否允许上传和访问，不需要写可执行 WebShell。测试系统是否只看最后几个字符：

```text
test.jsp
test.jsp.txt
test.txt.jsp
test.php5
test.JSP
image.jpg.jsp
```

也要检查系统是否相信前端：前端只允许选择图片时，后端是否真的检查；文件名是否可控；能否用代理工具在授权靶场改请求。

### ✅ 第2步完成标志

- 至少测试 3 种危险扩展名或伪装扩展名；
- 能说明系统是“拒绝上传”“允许上传但不能执行”还是“允许上传并可访问”；
- 保留上传页面截图、请求包或后端日志。

## 第3步：测试MIME类型、文件头与伪装文件

浏览器上传时会带 `Content-Type`，例如 `image/png`，但这个值来自客户端，可以被修改，服务器不能完全相信它。准备一个文本文件，内容为：

```text
COURSE_FAKE_IMAGE_TEST
```

把文件名改成：

```text
fake.png
```

上传后观察系统是否只因为扩展名是 `.png` 就接受；下载后内容是否仍是文本；后端是否检查文件头；是否把文件当图片预览导致异常。课程阶段不要求记住所有文件头，只要求理解：扩展名是用户可以改的，文件真实内容需要服务端检查。

### ✅ 第3步完成标志

- 完成一次“扩展名看起来正常、内容并非真实图片”的测试；
- 能说明 `Content-Type` 为什么不能完全相信；
- 能说明服务端为什么要做真实文件类型校验。

## 第4步：认识WebShell风险

WebShell可以理解为上传到Web服务器上的脚本入口。如果服务器把它当代码执行，攻击者可能通过浏览器控制服务器执行命令、读写文件。本课程不要求、不鼓励编写真实可用的 WebShell。我们只做无害标记页来证明“上传目录是否可能执行脚本”。

如果你使用 Java/Tomcat，可以准备一个只输出固定文字的 JSP 文件：

```jsp
<%@ page contentType="text/plain;charset=UTF-8" %>
COURSE_JSP_EXECUTION_TEST_ONLY
```

如果上传后访问该文件，浏览器看到固定文字，说明服务器可能执行了 JSP。注意：不要加入命令执行、文件管理、反连、持久化等功能。如果你使用 Flask，默认上传目录通常不会执行 Python 文件，但仍要测试是否能直接访问、是否能覆盖模板或静态文件。

本课程中的木马识别只包括：识别危险扩展名，识别脚本关键特征，检查上传目录是否出现异常脚本，清理课程无害样本，写检测与加固报告。不涉及免杀、隐藏、远控、传播、窃取数据等内容。

### ✅ 第4步完成标志

- 能解释 WebShell 的基本风险；
- 只使用无害标记页证明脚本是否可能被执行；
- 不编写、不上传、不连接真实命令执行型 WebShell；
- 能说明“允许上传脚本”和“脚本被服务器执行”之间的区别。

## 第5步：推荐工具认知——蚁剑、哥斯拉、冰蝎

### 5.1 为什么要认识这些工具

蚁剑、哥斯拉、冰蝎都是常见 WebShell 管理工具。它们的共同点是：当服务器上已经存在可连接的 WebShell 脚本入口时，工具可以通过 HTTP 请求与该入口交互，提供文件管理、环境信息查看、命令执行、数据库连接、代理转发等功能。

本课程让大家认识这些工具，不是为了让大家“学会控制服务器”，而是为了理解下面三件事：

1. 文件上传漏洞为什么危险；
2. 服务器为什么不能让上传目录执行脚本；
3. 防守方如何从上传文件、访问日志、异常请求中识别 WebShell 行为。

> **课程纪律**：本任务只允许在自己小组的网盘靶场中操作。没有老师授权、没有小组授权、不是自己搭建的靶场，一律不能连接、测试或尝试。不要把工具用于公网网站、校园系统、公司系统或同学私人系统。

------

### 5.2 三个工具的关系

| 工具            | 常见定位                                                     | 本任务中的学习方式               |
| --------------- | ------------------------------------------------------------ | -------------------------------- |
| 蚁剑 AntSword   | 跨平台 WebShell 管理工具，界面直观，适合教学中讲解连接流程、请求特征和防护思路 | 本任务选择它做详细讲解           |
| 哥斯拉 Godzilla | 功能较多，支持多种 Payload、加密器和插件，常见于红队和攻防演练场景 | 参考蚁剑理解，不展开危险功能     |
| 冰蝎 Behinder   | 以动态加密通信为特点的网站管理客户端，流量隐蔽性更强         | 参考蚁剑理解，重点关注检测和防护 |

三者功能类似，都是“客户端 + 服务端脚本入口”的模式。差别主要在连接方式、编码方式、通信加密、插件能力、支持的脚本类型和流量特征。对本课程而言，不要求比较谁更强，而要求理解：只要上传目录可以执行脚本，攻击面就已经非常危险。

### 5.3 本任务选择蚁剑做详细讲解

本任务以蚁剑作为详细讲解对象。哥斯拉、冰蝎只要求了解其功能类似、风险类似、防护思路类似，不要求逐项实践。

蚁剑的基本工作流程可以理解为：

```text
靶场中存在一个已授权的脚本入口
    ↓
蚁剑客户端填写入口URL、连接口令、脚本类型、编码方式
    ↓
客户端向该入口发送HTTP请求
    ↓
服务端脚本处理请求并返回结果
    ↓
客户端把结果展示成文件管理、环境信息等界面
```

这里最关键的是：蚁剑并不是凭空控制服务器。它需要服务器上已经存在可连接的脚本入口。如果你的上传目录不允许执行脚本，或者脚本类型被拦截，或者上传文件被重命名到非执行目录，工具就无法完成连接。

### 5.6 蚁剑连接配置项应该怎么看

在蚁剑中创建连接时，通常会看到类似配置项。这里不要求死记界面按钮，而要理解每个字段代表什么。

| 配置项        | 含义                             | 课程中应该怎么理解                 |
| ------------- | -------------------------------- | ---------------------------------- |
| URL 地址      | WebShell 脚本入口的访问地址      | 只能填写本组靶场地址               |
| 连接口令      | 客户端与服务端脚本约定的认证字段 | 不得使用真实密码，不得写入报告明文 |
| 脚本类型      | PHP、JSP、ASPX 等                | 与服务器技术栈有关                 |
| 编码方式      | 请求和响应内容如何编码           | 影响中文、路径、参数传输           |
| 请求头/Cookie | 模拟已登录状态或指定请求特征     | 只允许使用自己的课程测试账号       |
| 代理设置      | 通过代理转发请求                 | 本任务不使用                       |
| 测试连接      | 检查入口是否可访问、口令是否匹配 | 只能用于本组靶场                   |

你要注意：如果工具能连接成功，说明服务端已经存在高风险入口；如果工具不能连接，也不能直接说明系统安全，仍然要检查上传目录是否执行脚本、危险扩展名是否被拒绝、上传文件是否被重命名。

### 5.7 蚁剑详细使用流程：只做低风险验证

下面的流程只适用于自己小组的网盘靶场，并且只用于课程无害验证。

#### 第一步：确认靶场地址

示例：

```text
http://127.0.0.1:8080/
http://localhost:5000/
http://192.168.56.101:8080/
```

确认你访问的是自己小组靶场，不是校园系统，不是公网系统。

#### 第二步：确认上传风险是否存在

先不要打开工具，先完成前面的基础测试：

```text
1. 危险扩展名是否允许上传；
2. 上传目录是否可以直接访问；
3. 脚本文件是否会被服务器执行；
4. 服务器日志是否记录上传与访问行为。
```

如果系统已经禁止危险扩展名，并且上传文件存储在非执行目录，那么蚁剑、哥斯拉、冰蝎这类工具通常无法完成有效连接。

#### 第三步：只连接授权入口

可以在蚁剑中创建连接，填写：

```text
URL：本组靶场中的授权入口
连接口令：口令
脚本类型：与入口匹配
编码方式：默认或 UTF-8
```

注意：本任务不要求学生自己编写真实 WebShell，不要求从网上复制 WebShell，不要求上传可执行远控脚本。可以只完成工具界面认知、日志样例分析和修复验证。

#### 第四步：点击测试连接并截图

如果测试连接成功，记录：

```text
1. 测试时间；
2. 靶场地址；
3. 脚本类型；
4. 是否连接成功；
5. Web服务器访问日志中对应请求；
6. 应用日志中是否能定位上传者和访问者。
```

截图时要打码：

```text
1. 连接口令打码；
2. Cookie 打码；
3. Token 打码；
4. 真实路径中涉及个人信息的部分打码。
```

#### 第五步：不要使用危险功能

连接成功后，不要继续使用虚拟终端、文件管理、数据库管理、代理、端口转发等功能。本任务的目的不是“操作服务器”，而是证明：一旦上传目录能执行脚本，工具化管理会让风险急剧放大。

#### 第六步：修复后重新验证

完成上传安全加固后，再用同样的测试路径验证：

```text
1. 危险脚本扩展名无法上传；
2. 伪装文件无法通过真实类型校验；
3. 上传目录无法执行脚本；
4. 原演示入口已删除；
5. 蚁剑无法再次连接；
6. 日志中能看到被拒绝的上传行为。
```

### 5.8 哥斯拉、冰蝎如何参考蚁剑理解

哥斯拉和冰蝎不再单独展开详细步骤。你可以把它们理解为“连接方式、通信方式、插件能力不同的同类工具”。

学习时重点关注：

```text
1. 它们都需要服务端脚本入口；
2. 它们都通过HTTP/HTTPS请求与入口通信；
3. 它们都可能具有文件管理、命令执行、数据库管理等高危能力；
4. 它们的流量可能经过编码或加密；
5. 防护重点仍然是阻断上传、阻断执行、记录日志、清理入口。
```

不需要掌握：

```text
1. 如何生成真实木马；
2. 如何绕过查杀；
3. 如何隐藏连接；
4. 如何做内存马；
5. 如何反连；
6. 如何提权；
7. 如何横向移动。
```

对于本课程，哥斯拉和冰蝎只作为“同类工具风险认知”出现。报告中可以写：

```text
本任务以蚁剑作为详细演示工具。哥斯拉、冰蝎与蚁剑同属 WebShell 管理工具，均依赖服务端脚本入口与客户端通信。三者在加密方式、插件能力和支持脚本类型上有所不同，但防护思路一致：禁止危险脚本上传，上传目录禁止执行，上传文件重命名并存储到非Web根目录，通过后端下载接口统一鉴权与审计。
```

### 5.9 从防御角度观察工具请求

即使不使用危险功能，也可以从防御角度观察工具请求。你需要打开 Web 服务器访问日志，例如：

```text
access.log
localhost_access_log.txt
nginx/access.log
tomcat/logs/localhost_access_log.*
```

重点观察：

```text
1. 访问时间是否集中；
2. 请求路径是否指向上传目录；
3. 请求方法是 GET 还是 POST；
4. 是否出现可疑脚本扩展名；
5. User-Agent 是否异常；
6. 请求体大小是否异常；
7. 同一入口是否被多次访问；
8. 是否来自非预期IP；
9. 应用日志中是否能追溯到上传者。
```

报告中可以这样描述：

```text
在本组靶场中，上传目录允许直接访问脚本文件。使用课程授权入口进行连接测试时，Web服务器访问日志记录到来自测试机IP的POST请求，请求路径指向 /upload/user1/demo.jsp。该现象说明上传目录中的脚本文件能够作为服务端入口被访问。修复后，危险扩展名被拒绝，上传目录禁止脚本执行，同一路径访问返回下载或拒绝响应，工具无法连接。
```

### 5.10 WebShell 与普通文件的识别思路

从防御角度，识别 WebShell 不要只靠一个特征。应综合判断：

```text
文件维度：
1. 扩展名是否危险，例如 .jsp、.jspx、.php、.asp、.aspx、.ashx；
2. 是否存在双后缀，例如 image.jpg.jsp；
3. 文件名是否随机且异常；
4. 文件体积是否很小但功能很强；
5. 是否包含大量编码、混淆、压缩字符串；
6. 是否包含动态执行、反射调用、进程调用、文件读写等危险特征。
路径维度：
1. 是否出现在 upload、avatar、tmp、cache 等可写目录；
2. 是否位于 Web 根目录下；
3. 上传目录是否被 Web 容器解析脚本；
4. 是否与正常业务文件混放。
日志维度：
1. 上传后是否很快被访问；
2. 是否有持续 POST 请求；
3. 请求参数是否异常；
4. 是否出现非业务接口的高频访问；
5. 是否来自陌生 IP；
6. 是否绕过正常页面流程。
业务维度：
1. 上传者是否为普通用户；
2. 上传文件是否与网盘业务无关；
3. 是否在非上课时间出现异常访问；
4. 是否绕过文件列表直接访问上传路径。
```

### 5.11 本工具小节完成标志

- 能说清楚蚁剑、哥斯拉、冰蝎都是 WebShell 管理工具；
- 能说明三类工具都需要服务端脚本入口；
- 能说明为什么上传目录执行脚本会造成严重风险；
- 能以蚁剑为例说明连接配置项的含义；
- 能说明本课程禁止使用哪些危险功能；
- 能从日志中找到工具连接的痕迹；
- 能在修复后证明工具无法连接或上传脚本无法执行。

## 第6步：文件上传安全加固

课程阶段建议只允许 `.txt .pdf .png .jpg .jpeg .zip` 等安全类型，并根据网盘需求调整。危险脚本类型默认拒绝：

```text
.jsp
.jspx
.php
.php5
.asp
.aspx
.ashx
.py
.sh
.bat
.cmd
.exe
```

不要只写黑名单，因为危险类型太多，容易漏。更推荐使用白名单。

### 6.1 使用白名单限制扩展名

示例逻辑：

```text
允许：txt、pdf、png、jpg、jpeg、zip
拒绝：白名单之外的所有类型
```

不要根据用户提交的原始文件名直接判断，要先规范化：

```text
1. 去掉路径分隔符；
2. 统一转成小写；
3. 处理多后缀；
4. 拒绝空扩展名；
5. 拒绝超长文件名；
6. 拒绝包含控制字符的文件名。
```

------

### 6.2 不要直接使用用户原始文件名

不要直接使用用户原始文件名作为存储名。可以使用：

```text
UUID + 安全扩展名
```

例如：

```text
原始文件名：我的照片.jpg
实际保存名：b8a7f3b1-9f77-4c2a-8c22-2026test.jpg
```

原始文件名只作为展示字段保存，展示时还要做 XSS 输出编码。

------

### 6.3 上传目录禁止脚本执行

上传目录应该只用于存储，不应该让 Web 服务器执行其中脚本。更安全的做法是：

```text
1. 上传文件存放在 Web 根目录之外；
2. 用户访问文件时必须经过后端下载接口；
3. 下载接口统一做登录校验和文件归属校验；
4. Web服务器配置禁止上传目录执行脚本；
5. 上传目录不给执行权限。
```

如果是 Nginx、Apache、Tomcat 或 Spring Boot 项目，要检查静态资源映射规则，避免把上传目录直接暴露成可执行路径。

------

### 6.4 检查真实文件类型

服务端不能完全相信：

```text
1. 文件扩展名；
2. 浏览器传来的 Content-Type；
3. 前端输入框限制；
4. 用户自己填写的文件类型。
```

应结合：

```text
1. 扩展名白名单；
2. MIME类型检查；
3. 文件头检查；
4. 文件大小限制；
5. 内容安全扫描；
6. 业务场景限制。
```

------

### 6.5 限制文件大小、数量和空间

同时限制：

```text
1. 单文件大小；
2. 单用户总空间；
3. 单用户每日上传数量；
4. 文件名长度；
5. 压缩包解压层数；
6. 压缩包解压后总大小。
```

不要允许无限制上传，否则可能引发磁盘打满、拒绝服务、日志膨胀等问题。

------

### 6.6 日志与告警

至少记录：

```text
1. 上传者用户ID；
2. 上传时间；
3. 来源IP；
4. 原始文件名；
5. 实际保存名；
6. 文件大小；
7. 检测出的文件类型；
8. 是否通过校验；
9. 拒绝原因；
10. 下载或访问记录。
```

日志里不要记录明文密码、完整 Cookie、完整 Token。发现危险扩展名、双后缀、脚本内容、上传后立即访问等行为，应在报告中标记为异常事件。

## 漏洞报告至少写清楚

- 漏洞类型：例如文件上传漏洞、危险脚本上传、上传目录脚本执行、WebShell 风险。
- 漏洞位置：完整 URL、接口路径、请求方法、关键参数。
- 测试环境：本机、虚拟机或本组课程靶场；测试时间；测试账号。
- 测试文件：文件名、扩展名、MIME类型、是否为无害样本。
- 工具认知：是否观察蚁剑、哥斯拉、冰蝎等工具；如果使用蚁剑，只能写本组靶场、授权入口、测试连接和日志观察。
- 复现步骤：从登录、上传、访问到观察结果，每一步都要截图或保存请求包。
- 影响说明：能造成什么后果，不能夸大；例如“上传目录可执行脚本，存在被 WebShell 工具连接的风险”，不要写成“已经完全控制服务器”。
- 日志证据：上传日志、访问日志、拒绝日志、修复后验证日志。
- 修复建议：说明根因、给出修复方式，并附修复后同样步骤无法成功的证明。

------

## 修复时的共同原则

1. 不要只在前端过滤。浏览器里的限制都可以被 F12、代理工具或脚本绕过，后端必须做真正校验。
2. 不要只黑名单过滤某几个字符。优先采用白名单、参数化查询、框架内置安全机制、权限统一拦截。
3. 不要修一个接口漏一个接口。文件展示、下载、删除、重命名、分享等同类接口都要统一检查。
4. 修复后一定要用“原来的测试参数和测试文件”再测一遍，证明漏洞确实失效。
5. 上传目录不要执行脚本。用户可以存文件，但不能把服务器变成他的运行环境。
6. 工具验证不能代替代码审计。工具连不上，不等于一定安全；工具连得上，说明风险已经很高，必须修复根因。
7. 日志必须能追踪。至少能知道谁上传、何时上传、保存在哪里、是否被访问、是否被拒绝。

------

## 最后的提醒

上传功能的安全目标很简单：用户可以存文件，但不能把服务器变成他的运行环境。蚁剑、哥斯拉、冰蝎这类工具让我们更直观地看到 WebShell 风险：一旦脚本入口存在，攻击者就可能把一个普通上传点变成服务器控制入口。

本任务真正要学会的不是“使用工具控制服务器”，而是理解为什么危险文件不能上传、为什么上传目录不能执行脚本、为什么日志必须可追踪、为什么修复后要再次验证。只要你做到限制类型、重命名、非执行目录、后端下载、记录日志，上传风险就会明显下降。
