# 我的Web网盘攻防战 —— 阶段二任务3：XSS跨站脚本测试

## 写在前面：你输入的是文字，浏览器看到的可能是代码

网盘系统里有很多“会显示用户输入”的地方：用户名、文件名、个人简介、文件备注、搜索关键词、分享标题。只要后端把这些内容原样放进HTML页面，浏览器就可能把它们当作代码执行。这就是 XSS（Cross-Site Scripting，跨站脚本）。本任务要学习的不是“弹窗好玩”，而是理解所有显示到页面上的用户输入，都必须进行安全输出编码。

> **边界提醒**：本任务只允许在自己小组的网盘靶场、课程指定互测靶场、虚拟机或本机 `localhost` 中完成。不要扫描、爆破、上传、探测任何未授权网站、校园系统、云服务或他人真实业务系统。所有攻击动作都必须可回滚、可截图、可复现，不以破坏数据为目标。

## 第1步：找到可能的输出点

请先在网盘中找出“用户输入会被页面显示”的位置。例如注册用户名显示在欢迎语，文件列表显示上传文件名，搜索页面显示“你搜索的是 xxx”，文件备注、分享说明、个人简介、错误页面显示用户输入的文件名。

先用一个特殊但安全的标记字符串测试：

```text

```

如果你输入后能在HTML源码或页面上看到这个字符串，说明这里是一个输出点。

## 第2步：反射型XSS探测

反射型XSS是指用户输入没有保存到数据库，而是通过请求参数立即返回到页面。例如搜索功能：`/search?keyword=abc`，页面显示“你搜索的是：abc”。如果 `keyword` 原样进入HTML，就可能存在反射型XSS。

课程中先用最简单的弹窗作为证明：

```html
<script>alert('XSS_TEST')</script>
```

如果页面弹窗，说明浏览器把你的输入当作脚本执行了。如果 `<script>` 被过滤，不代表安全。你还需要观察输入是否被完整显示，尖括号是否被转义为 `&lt;` 和 `&gt;`，引号是否影响了HTML属性，页面源码中你的输入处在什么上下文。

常见输出上下文包括：

```html
<p>搜索关键词：用户输入</p>
<input value="用户输入">
<script>var keyword = "用户输入";</script>
```

不同位置需要不同编码方式。只做一个简单替换，很容易漏掉。

---

## 第3步：存储型XSS探测

存储型XSS是指用户输入被保存到数据库或文件系统，之后每个访问该页面的人都会看到并触发。例如用户名、文件名、文件备注。网盘项目中最典型的是文件名显示。你可以在本机创建一个文件，文件名包含测试标记：

```text
xss_test_<script>alert('XSS_FILE')</script>.txt
```

有些操作系统不允许文件名包含某些字符，这时可以换成备注、昵称、分享标题等字段测试。测试时用用户A提交，用用户B访问同一页面或分享页面。若用户B也触发，说明这不只是“自己影响自己”，而是能影响其他访问者。

---

## 第4步：分析漏洞原因

XSS的根因通常是：后端或模板把用户输入原样拼接进HTML；关闭了模板引擎自动转义；为了“允许富文本”而直接信任HTML；只过滤了 `<script>`，但没有按上下文编码；文件名、错误信息等“看起来不像输入”的地方被忽略。

同样是用户输入，出现在HTML正文、HTML属性、JavaScript字符串中，修复方法不同。修复时不能只写一个全局替换，而要根据上下文使用正确编码。

---

## 第5步：修复XSS

如果你使用模板引擎，尽量开启默认自动转义。Flask/Jinja2 默认 `{{ value }}` 会做HTML转义，不要随便使用 `|safe`；Thymeleaf 优先使用 `th:text`，不要用 `th:utext` 显示不可信内容；JSP 可使用 JSTL `<c:out>` 或类似转义输出方式。

后端返回HTML时，至少要把 `<`、`>`、`"`、`'`、`&` 转义。修复后，用户输入的 `<script>alert(1)</script>` 应该作为普通文本显示在页面上，而不是执行。对于用户名、备注、分享标题等字段，还可以加长度限制和字符白名单，但输入限制不能替代输出编码。

### 漏洞报告至少写清楚

- 漏洞类型：例如 SQL注入 / XSS / CSRF / 越权下载。
- 漏洞位置：完整 URL、接口路径、请求方法、关键参数。
- 测试环境：本机、虚拟机或课程互测靶场；测试时间；测试账号。
- 复现步骤：从登录、构造请求到观察结果，每一步都要截图或保存请求包。
- 影响说明：能造成什么后果，不能夸大；例如“可绕过登录进入文件列表”，不要写成“可控制服务器”。
- 修复建议：说明根因、给出修复方式，并附修复后同样步骤无法成功的证明。

### 修复时的共同原则

1. 不要只在前端过滤。浏览器里的限制都可以被 F12、代理工具或脚本绕过，后端必须做真正校验。
2. 不要只黑名单过滤某几个字符。优先采用白名单、参数化查询、框架内置安全机制、权限统一拦截。
3. 不要修一个接口漏一个接口。文件展示、下载、删除、重命名、分享等同类接口都要统一检查。
4. 修复后一定要用“原来的攻击参数”再测一遍，证明漏洞确实失效。

## 最后的提醒

XSS最容易被初学者低估，因为它常常表现为“弹了个窗”。但真正的问题是：浏览器执行了不该执行的代码。只要你记住“用户输入显示到页面前必须编码”，就能避免大量前端安全问题。
